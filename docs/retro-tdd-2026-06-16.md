## 2. 짜는 과정에서 발견한 것

### 예상과 달랐던 / 직접 확인해야 했던 동작
- **연도 넘김을 놓칠 뻔함**: `11/30 + 3개월`을 머리로 계산하다 연도(2025)를 빠뜨림. "예상→테스트로 확인" 절차가 이걸 잡음. JDK는 overflow가 아니라 **항상 그 달 마지막 유효일로 clamp**한다는 걸 테스트로 못박음.
- **리포트가 틀린 케이스 2건 발견**:
  - `getHomeToday`를 "now() 의존이라 테스트 불가"로 분류했지만 실제론 **`date`를 인자로 받는 파라미터화 메서드** → 이미 테스트 가능 (리포트가 보수적으로 틀림).
  - 백신 한도 update 비대칭을 처음엔 "우회 버그"로 의심했으나, 코드를 정독하니 **올바른 설계**였음 — 카운트가 자기 자신을 포함하므로 이미 켜진 알림 재검사는 *거짓 거부*를 낳음. 우회 경로(OFF→ON)는 항상 검사하므로 한도 초과 불가. → **테스트로 "이 비대칭은 의도된 것"을 잠가** 누가 잘못 "고치는" 걸 방지.

### 잠재 결함 (테스트가 드러낸 진짜 버그 3건)
1. `Subscription.renew`가 만료시각을 **무조건 덮어씀** → Apple/Google이 **재전송하거나 순서 뒤바뀐** 갱신 알림(공식적으로 순서 보장 안 됨)을 보내면 만료가 과거로 후퇴 → 유저가 돈 낸 구독이 **조기 만료**.
2. `JwtTokenProvider`가 **issuer/audience 미설정·미검증** → 같은 비밀키로 서명되기만 하면 발급 주체/수신자 무관하게 통과 → 토큰 혼용 위험.
3. `YearMonth.now()`가 **ZoneId 없이** 호출 → ECS(UTC) 기준이라 한국 자정~오전 9시 사이 월 한도 리셋이 **9시간 지연** → 유저가 새 달인데도 차단.

### 리팩터한 것 (왜)
- `RecurrenceTypeTest`: 개별 메서드 4개 → `@ParameterizedTest`로 통합. **이유**: 경계 케이스 추가가 한 줄이면 되게, 중복 제거. (테스트 코드도 리팩터 대상)
- `OcrUsageService`: `YearMonth.now()` 2곳 중복 → `currentYearMonth()` 헬퍼로 추출. **이유**: KST 수정과 동시에 DRY, 호출부 한 곳만 진실의 원천.

## 3. 구조 변경 (Clock 주입) — before/after

핵심 아이디어: **"시간을 의존성으로 다룬다"** — 직접 `now()` 호출은 테스트에서 경계(만료 1ms 전후, 월말 자정)를 재현 불가능하게 만든다.

| 위치 | Before | After |
|---|---|---|
| `SubscriptionStatusResponse.from` | `...isAfter(LocalDateTime.now())` (inline) | `from(User, Clock)` 추가 + `now(clock)`. 기존 `from(User)`는 시스템시계로 위임(호환) |
| `SubscriptionService` | Clock 없음, `from(user)` 호출 | `private final Clock clock` 주입, 3개 호출부 `from(user, clock)` |
| `OcrUsageService` / `SymptomCheckService` | `YearMonth.now()` (서버 기본 TZ) | `private final Clock clock` 주입, `YearMonth.now(clock.withZone(KST))` |
| 신규 `ClockConfig` | — | `@Bean Clock` (운영=systemDefaultZone, 테스트=`Clock.fixed(...)`) |
| `JwtTokenProvider` | issuer/audience 없음 | `.issuer/.audience` 발급 + `.requireIssuer/.requireAudience` 검증 (※ 만료 Clock 주입은 후속 과제로 남김) |

**효과**: 운영 경로까지 주입된 시계가 흐르게 되어, 앞으로 만료 스케줄러 등도 같은 `Clock` 빈을 가짜로 갈아끼워 통째로 테스트 가능.

## 5. 테스트로 박았지만 도메인상 재검토 필요한 지점

1. **`expiresAt == null && 유료티어 → active=true`** — 현재 동작을 그대로 잠갔지만, 데이터 손상 시 *영구 무제한 구독*이 됨. 정책적으로 null을 어떻게 볼지(=비활성 처리? NOT NULL 제약?) 재검토 필요. *지금은 "동작 보존"만 하고 정책 변경은 분리.*
2. **단조 renew가 환불 후 부활을 허용** — CANCELLED 구독에 *미래* 갱신 알림이 오면 단조 규칙상 다시 ACTIVE가 됨. 환불 이후 재활성 시나리오가 비즈니스적으로 맞는지 확인 필요(엣지).
3. **issuer/audience·KST가 하드코딩 상수** — KR 단일앱엔 충분하나, 다중 환경/국제화 시 설정값화 필요. 특히 **배포 시 기존 토큰 무효화**(401→자동 재발급) 영향은 운영상 인지하고 배포 타이밍 잡아야 함.
4. **공유 펫의 백신 한도가 소유자(owner) 티어 기준** — 코드상 의도된 듯하나 제품 결정으로 명시 필요.
5. **증상체크 나이 계산은 여전히 `LocalDate.now()`** (KST/Clock 미적용) — 영향 작아 이번 범위에서 제외했지만 일관성 차원에서 후속 정리 대상.

## 면접용 한 문단 (STAR)
> **상황**: 출시된 앱인데 백엔드 핵심 로직에 테스트가 없어 회귀 안전망이 전무했다. **과제**: 무작정 커버리지를 올리기보다 *틀리면 돈·권한이 깨지는* 지점을 골라 TDD로 다지기로 했다. **행동**: 결제 webhook·JWT·월 할당량을 red→green으로 짜는 과정에서, ① webhook 재전송 시 구독이 조기 만료되는 버그(단조 불변식으로 수정), ② JWT issuer/audience 미검증, ③ 월 한도가 서버 UTC를 따라 한국 기준 9시간 어긋나는 버그를 발견·수정했다. 시간을 `Clock`으로 주입해 경계를 결정적으로 검증되게 리팩터했다. **결과**: 테스트 0→30개, 실제 버그 3건 수정. 또한 "비대칭=버그"라는 초기 가정이 정독 결과 *올바른 설계*임을 밝혀 그대로 잠갔다 — TDD가 단순 검증이 아니라 *설계 이해를 강제*한다는 걸 체감했다.
